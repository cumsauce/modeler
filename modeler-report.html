Modeler session issues

Problems hit while building a detailed AK-47 model (53 parts, two procedural materials) through the modeler MCP tools. One crash bug, plus several smaller rough edges.

Crash

1. silhouette ops make the server exit with SIGSEGV

Any apply_ops batch that contained silhouette items killed the server. The tool returned:

daemon error: server closed stdout (the modeler server exited: code -11: killed by SIGSEGV)

It happened twice:

  • First crash: a mixed batch of about 30 items (primitives, sweeps, a loft, silhouettes with side, top and sometimes front outlines, some with arc ring items, and materials).
  • Second crash: a batch of only six silhouette items. They used plain point outlines, with no arcs, no front, and no smooth. The same primitives, sweeps and loft from the first batch had already been applied on their own without trouble, so silhouette is the likely cause.

The parts were small, real-world gun parts: a few centimeters across, with round from 0.002 to 0.008 m. My guess is that the default voxel resolution or the corner rounding fails at that small scale. Example item from the second batch:

{"type":"silhouette","name":"gas_block",
 "side":[[0.345,0.985],[0.375,0.985],[0.375,1.05],[0.355,1.05]],
 "top":[[-0.015,0.345],[0.015,0.345],[0.015,0.375],[-0.015,0.375]],
 "round":0.003}

Workaround: I built each side outline as an extrude with rotation: {z: 90} instead (profile given as [y, z], extruded across x). That worked every time.

Data loss

2. A crash wipes the open document

  • After each restart, scene_summary showed an empty document named model. My document ak47, its name, every op and every part from earlier calls were gone.
  • The materials I had made with material_ops also seemed to disappear, so I rebuilt them before going on.
  • Saving the document's ops automatically, or keeping a crash journal, would mean one bad op doesn't wipe a whole session's work.
Docs

3. describe_op doesn't cover material nodes

describe_op only knows apply_ops item types. Asking it about material nodes such as noise, ramp, warp or output returns "unknown type". Yet the material_ops description says "describe_op(kind) has an example and schema for every node type". To find the node list and required fields, I had to send material_ops calls that I expected to fail and read the errors (for example, that noise needs size and remap needs from). The error messages were clear, but a real schema lookup would be faster.

Usability

4. ops_file can't be used without a project

I generated a batch of 112 items with a script and passed it through ops_file. Even with an absolute path, the call was refused with "this call has no project to read it from". I had to paste the whole batch inline instead. It would help if ops_file took an absolute path when no project is set, or if the error said how to set a project up.

Minor

5. Smaller notes

  • material_catalog once switched the active document without saying so, because another agent's document (fs-room-pit) had been active. The tool did report it afterwards, which was helpful.
  • Too many warnings: the near-flush and near-touch warnings fill the summary on mechanical models, where parts sit a millimeter apart on purpose (57 warnings for 53 parts). A way to turn them down, or to group them, would help.
  • Material ops for hidden or helper parts (boolean inputs) are accepted silently. That's fine, but it means the "default material" warnings only show for parts you can see.
What worked well

6. What went smoothly

  • Batches either applied fully or not at all, and the error messages named the exact field, so problems were quick to fix.
  • extrude, loft along a path (a curved magazine), sweep, boolean and repeat all behaved as documented.
  • Procedural wood grain (noise stretched along the grain and warped) and the worn-steel material took only two or three calls each.
